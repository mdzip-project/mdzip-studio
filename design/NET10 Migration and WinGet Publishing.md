# .NET 10 Migration & WinGet Publishing

## Purpose

Two intertwined efforts, sequenced as one:

1. **Migrate the ecosystem's .NET footprint from .NET 8 → .NET 10 (LTS).**
2. **Publish MDZip Studio (and optionally the CLI) on the Windows Package Manager (WinGet).**

They are combined deliberately: the WinGet manifest declares a .NET runtime dependency, so it should target the runtime we intend to ship on. Shipping the new WinGet package on .NET 8 would mean re-revising and re-validating the manifest within months.

## Why now

As of 2026-06-25:

- **.NET 8 (LTS)** — end of support **Nov 2026** (~4.5 months out). Migration is required regardless.
- **.NET 9 (STS)** — at/past EOL (~May 2026). **Skip entirely.**
- **.NET 10 (LTS)** — released Nov 2025, supported through **Nov 2028**, ~7 months of patches (stable, not bleeding-edge).

This is a clean **LTS → LTS** jump.

## Affected components

| Component | Repo | Current target | Runtime package |
|---|---|---|---|
| `mdzip.core` (.NET format lib) | (core .NET repo) | `net8.0` (`lib/net8.0`) | shared dependency, no runtime of its own |
| Preview handler (`mdz.WinPrev`) | `mdzip-win-prev` | `net8.0-windows` | `Microsoft.WindowsDesktop.App` |
| CLI | (CLI repo, e.g. `mdzip-cli`) | `net8.0` | `Microsoft.NETCore.App` (or none if AOT) |
| MDZip Studio (this repo) | `mdzip-studio` | bundles built handler | downloads/declares desktop runtime |

**Key coupling:** `mdzip.core` is shared by the preview handler and the CLI. Bumping core to net10 forces both consumers to move (or forces core to multi-target indefinitely). The clean path is to retire net8 everywhere in one sweep.

## Packaging & bundling decisions

Organizing principle: **bundle downward** (a heavier component may ship a lighter one), **not upward** (a lighter, more-portable component should not ship a heavier, platform-locked one). Weight/portability order:

```
Studio (Electron GUI, heaviest, Windows desktop)
  > preview handler (Windows shell extension, WindowsDesktop runtime, HKLM/elevation)
    > CLI (lightest, ideally cross-platform AOT, no runtime)
      > mdzip.core (library)
```

| Decision | Verdict | Rationale |
|---|---|---|
| Preview handler shipped *inside* the CLI | **No** | Inverts layering: Windows-locks the CLI payload (dead weight on Linux/macOS), drags the WindowsDesktop runtime back in, and undoes the AOT "no runtime" win. At most, expose an optional Windows-only `mdzip preview register\|unregister` command that registers a *separately provided* handler dir. Preview handler stays owned by `mdzip-win-prev`; **Studio remains its primary distribution vehicle.** |
| CLI shipped *inside* Studio | **Yes, opt-in** | Natural downward bundling (VS Code `code` model). Cheap if the CLI is AOT/self-contained. Add it to `extraResources` and offer an opt-in "Add `mdzip` to PATH" installer checkbox, mirroring the existing Explorer-integration opt-in. |

Constraints on bundling the CLI in Studio:
- **PATH scope must match install scope** (per-user vs machine) and the uninstaller must remove it.
- **Avoid duplicate `mdzip` binaries** vs a standalone CLI WinGet install: use the same `PackageIdentifier`/version, or have the bundled copy detect a standalone install and skip PATH registration.
- The CLI is **still published independently** (WinGet, cross-platform) for headless/server users who don't want Electron.

## Open questions / risks

- **SmartScreen on unsigned installer** — WinGet accepts unsigned installers, but users see SmartScreen prompts until reputation builds. Code signing is intentionally out of scope for now; this only affects perceived trust, not eligibility.
- **Sandboxed validation + in-installer .NET download** — mitigated by the `PackageDependencies` approach in Phase 6. Without it, the `aka.ms` download can fail in WinGet's restricted-network validation VM.
- **Default scope ≠ previewer** — inherent to the design (previewer needs HKLM/elevation). Documentation item, not a defect.
- **electron-updater vs WinGet** — decide the update source of truth so the two upgrade paths don't conflict for machine-scope installs.
- **CLI repo location / `mdzip.core` reference** — confirm the CLI actually references `mdzip.core` and that its dependencies are AOT-compatible (Phase 0).
